🏗️ Sesión 2: Modelado de Datos (Data Modeling)
🎨 Herramientas de Visualización: PlantUML y Mermaid
En el proceso de modelado de datos, la comunicación visual es tan importante como la estructura. Las herramientas de Diagramas como Código (Diagrams as Code) como PlantUML y Mermaid han simplificado enormemente la creación y el mantenimiento de diagramas ER (Entidad-Relación) y de esquemas dimensionales.


PlantUML y Mermaid permiten describir un diagrama (entidades, atributos, y relaciones) mediante una sintaxis de texto simple en lugar de usar un editor gráfico.


¿Para qué sirven en el Modelado de Datos?
1. Agilidad y Mantenimiento: Es más fácil versionar y auditar un archivo de texto plano que un archivo binario (.png o .vsdx). Los cambios en el modelo se reflejan instantáneamente al modificar el código.
2. Documentación Automática: Permiten incrustar los diagramas directamente en la documentación técnica (como se ha visto en los ejemplos anteriores) o en sistemas de gestión de conocimiento (wikis, Notion, etc.).
3. Claridad en la Comunicación: Facilitan a arquitectos, desarrolladores y analistas entender la estructura de la base de datos de un vistazo, evitando ambigüedades.


¿Qué es el Modelado de Datos?
Si la arquitectura es el plano de la ciudad, el Modelado de Datos es el diseño de los edificios. Determina cómo se estructuran las tablas, qué relación tienen entre sí y cómo se garantiza que el sistema sea eficiente.
Modelar datos es el proceso de representar la estructura de la información de un dominio del mundo real para que pueda ser almacenada y gestionada en un sistema.


¿Qué modelamos realmente?
Cuando modelamos datos, estamos modelando:
* Entidades → objetos del mundo real (Cliente, Producto, Estudiante)

* Atributos → propiedades de esas entidades (nombre, apellido, fecha, estado, precio, cargo)
   * Cliente (nombre, apellido)
   * Pedido (fecha, estado)
   * Producto (nombre, precio)
   * Empleado (nombre, cargo)
   * Sucursal (nombre, dirección)
Restricciones → reglas del negocio (el precio no puede ser negativo y debe ser mayor a cero)
   * Un Cliente debe tener un nombre y apellido.
   * El precio de un Producto debe ser mayor a 0.
   * Un Pedido debe tener al menos un Producto (contiene Producto).
   * Un Empleado debe tener un cargo definido.

Modelado como proceso iterativo:
El modelado no es estático. Es:
      * Iterativo

      * Evolutivo

      * Dependiente del contexto (puede ser modelado OLTP vs OLAP)
Relación con Arquitectura de Datos
Dentro de la arquitectura de datos, el modelado define:
         * La estructura del almacenamiento

         * La forma en que se integran los sistemas

         * La eficiencia de consultas

         * La base para analítica y BI

Es uno de los pilares fundamentales de cualquier arquitectura de datos sólida.

1. Modelo Conceptual (El "Qué")
Es la visión de más alto nivel. Aquí no nos importa la tecnología, sólo la lógica del negocio.
               * Objetivo: Identificar las entidades (objetos) y cómo se relacionan.
               * Público: Stakeholders, Gerentes, dueños del negocio y analistas.
               * Componentes: Entidades (ej. Cliente, Producto) y Relaciones (ej. el Cliente compra un Producto).
               * Regla de oro: No se definen tipos de datos ni claves técnicas.
               * Para modelar conceptualmente se pueden utilizar diagramas UML como el diagrama de clases o más comúnmente el diagrama entidad relación ER (Entidad Relación). A continuación se utiliza un diagrama de clases UML:

Concepto previo: 
Una clave primaria (Primary Key) es un atributo o un conjunto de atributos en una tabla de una base de datos que identifica de forma única a cada registro (fila) de esa tabla. Sus características principales son:
               * Unicidad: No puede haber dos registros con el mismo valor de clave primaria.
               * No nulidad: El valor de la clave primaria no puede ser nulo (vacío).
               * Identificación: Sirve como el identificador principal para acceder a un registro específico.
Generalmente esta clave primaria se genera automáticamente (1,2,3,...)
               * Tabla: Estudiantes: La clave primaria es IdEstudiante. Cada valor (1, 2, 3) identifica de manera única a un estudiante. No puede haber dos estudiantes con el mismo IdEstudiante, ni puede ser un valor nulo.
               * Tabla: Cursos: La clave primaria es IdCurso. Cada valor (101, 102, 103, 104) identifica un curso específico.
               * Tabla: Inscripciones: La clave primaria es IdInscripcion. Es el identificador único para cada registro de inscripción.
Qué es una clave foránea:
Una clave foránea (Foreign Key) es un atributo o un conjunto de atributos en una tabla (la tabla "hija" o referenciadora) que hace referencia a la clave primaria de otra tabla (la tabla "padre" o referenciada). Su propósito es establecer y mantener un vínculo entre dos tablas. Sus características principales son:
               * Vínculo: Crea una relación entre la tabla donde se define y la tabla a la que referencia.
               * Referencia: Su valor debe coincidir con un valor existente en la clave primaria de la tabla referenciada (o ser nulo, dependiendo de las reglas de negocio).
               * Integridad: Impide que se ingresen valores en la tabla hija que no existan en la tabla padre, manteniendo la coherencia de los datos.


               * Tabla: Inscripciones: Esta tabla contiene dos claves foráneas que establecen vínculos con las otras dos tablas:
               * IdEstudiante (FK): Esta es una clave foránea que hace referencia a la clave primaria IdEstudiante de la tabla Estudiantes. Esto asegura que solo se puedan registrar inscripciones para estudiantes que realmente existen en la tabla Estudiantes (Integridad Referencial). Por ejemplo, el valor 1 en IdEstudiante (FK) de Inscripciones se vincula al registro de Sofía Mendieta en la tabla Estudiantes.
               * IdCurso (FK): Esta es una clave foránea que hace referencia a la clave primaria IdCurso de la tabla Cursos. Esto garantiza que solo se puedan inscribir estudiantes en cursos que existen en la tabla Cursos. Por ejemplo, el valor 101 en IdCurso (FK) de Inscripciones se vincula al curso "Introducción a la Programación" en la tabla Cursos.
En resumen, las claves foráneas (IdEstudiante (FK) e IdCurso (FK)) en la tabla Inscripciones son cruciales para mantener la coherencia y las relaciones entre las tablas, impidiendo inscripciones a estudiantes o cursos inexistentes.
En el modelo lógico, aquí empezamos a darle estructura. Es el puente entre el negocio y la técnica. Sigue siendo independiente de la base de datos (puedes usarlo para MySQL o PostgreSQL por igual).
               * Objetivo: Definir la estructura de los datos y sus reglas.
               * Público: Arquitectos de datos y desarrolladores.
               * Componentes: Atributos (Nombre, Fecha, Precio), Claves Primarias (PK) y Claves Foráneas (FK), y se resuelven relaciones de muchos a muchos.
               * Regla de oro: Aquí ya aplicamos la Normalización (que veremos más adelante).
               * Aquí las tablas varios a varios se parten. Por ejemplo en el diagrama conceptual decimos un estudiante se matricula en varios cursos, aquí creamos la tabla inscripción o matrícula explícitamente.


Modelado Lógico:

  id_carrera <<PK>>
  nombre
}

  id_estudiante <<PK>>
  nombres
  apellidos
  fecha_nacimiento
  id_carrera <<FK>>
}

  id_profesor <<PK>>
  nombres
  apellidos
  especialidad
}


class Curso {
  id_curso <<PK>>
  nombre
  creditos
  id_carrera <<FK>>
  id_profesor <<FK>>
}


class Inscripcion {
  id_inscripcion <<PK>>
  id_estudiante <<FK>>
  id_curso <<FK>>
  fecha_inscripcion
  nota_final
}

3. Modelo Físico (El "Dónde")
Es la implementación real en un motor de base de datos específico. 
               * Objetivo: Optimizar el rendimiento y el almacenamiento.
               * Público: DBAs y Desarrolladores de Datos.
               * Componentes: Tipos de datos específicos (VARCHAR, INT, JSONB), índices, particiones, vistas y triggers.
               * Regla de oro: Se adapta a las capacidades del motor (ej. Snowflake vs. Oracle).
Ejemplo Implementación SQL – PostgreSQL


CREATE TABLE carrera (
    id_carrera SERIAL PRIMARY KEY,
    nombre VARCHAR(100) NOT NULL UNIQUE
);


CREATE TABLE profesor (
    id_profesor SERIAL PRIMARY KEY,
    nombres VARCHAR(100) NOT NULL,
    apellidos VARCHAR(100) NOT NULL,
    especialidad VARCHAR(100)
);


CREATE TABLE estudiante (
    id_estudiante SERIAL PRIMARY KEY,
    nombres VARCHAR(100) NOT NULL,
    apellidos VARCHAR(100) NOT NULL,
    fecha_nacimiento DATE,
    id_carrera INT NOT NULL,
    CONSTRAINT fk_estudiante_carrera
        FOREIGN KEY (id_carrera)
        REFERENCES carrera(id_carrera)
        ON DELETE RESTRICT
);


CREATE TABLE curso (
    id_curso SERIAL PRIMARY KEY,
    nombre VARCHAR(100) NOT NULL,
    creditos INT NOT NULL CHECK (creditos > 0),
    id_carrera INT NOT NULL,
    id_profesor INT NOT NULL,
    CONSTRAINT fk_curso_carrera
        FOREIGN KEY (id_carrera)
        REFERENCES carrera(id_carrera),
    CONSTRAINT fk_curso_profesor
        FOREIGN KEY (id_profesor)
        REFERENCES profesor(id_profesor)
);


CREATE TABLE inscripcion (
    id_inscripcion SERIAL PRIMARY KEY,
    id_estudiante INT NOT NULL,
    id_curso INT NOT NULL,
    fecha_inscripcion DATE NOT NULL,
    nota_final NUMERIC(4,2) CHECK (nota_final BETWEEN 0 AND 20),
    CONSTRAINT fk_inscripcion_estudiante
        FOREIGN KEY (id_estudiante)
        REFERENCES estudiante(id_estudiante)
        ON DELETE CASCADE,
    CONSTRAINT fk_inscripcion_curso
        FOREIGN KEY (id_curso)
        REFERENCES curso(id_curso)
        ON DELETE CASCADE,
    CONSTRAINT unique_estudiante_curso
        UNIQUE (id_estudiante, id_curso)
);


CREATE INDEX idx_estudiante_carrera ON estudiante(id_carrera);
CREATE INDEX idx_curso_carrera ON curso(id_carrera);
CREATE INDEX idx_inscripcion_estudiante ON inscripcion(id_estudiante);
CREATE INDEX idx_inscripcion_curso ON inscripcion(id_curso);

Cardinalidad (Las Reglas del Negocio)
La cardinalidad define cuántas instancias de una entidad se relacionan con cuántas de otra. Esto es lo que suele confundir a los estudiantes, así que estos tres casos son clave:
               1. Uno a Uno (1:1): Un Ciudadano tiene un solo Pasaporte. (Poco común, a veces se fusionan en una tabla).
               2. Uno a Muchos (1:N): Un Cliente puede tener muchos Pedidos, pero un Pedido pertenece a un solo cliente. (Es el más común).
               3. Muchos a Muchos (N:M): Un Estudiante puede inscribirse en muchos Cursos, y un Curso puede tener muchos Estudiantes.
               * Es la más común en sistemas OLTP.

Notación Crow´s Foot


Cada línea de conexión tiene dos símbolos en sus extremos. Para leerla correctamente, siempre mira el extremo opuesto a la tabla desde donde empiezas.
Los símbolos representan dos cosas: Cardinalidad (el máximo) y Opcionalidad (el mínimo).
Los Símbolos Clave:
               * La "Pata" (tres líneas): Significa Muchos (N).
               * La Línea Recta (perpendicular): Significa Uno (1).
               * El Círculo: Significa Cero (Opcional).
Combinaciones Comunes:
Símbolo
	Significado
	Lectura
	--||
	Uno y solo uno
	Obligatorio, exactamente 1.
	--|{
	Uno o muchos
	Obligatorio, al menos 1.
	--o|
	Cero o uno
	Opcional, máximo 1.
	--o{
	Cero o muchos
	Opcional, pueden ser N o ninguno.
	________________


2. Notación en Mermaid (ER Diagrams)
Mermaid utiliza una sintaxis de texto plano muy intuitiva. La estructura básica es: 
ENTIDAD1 relación ENTIDAD2 : "verbo".
Sintaxis de los conectores:
Para dibujar los símbolos anteriores en Mermaid, usamos estos caracteres:
               * Lado de "Uno": | (uno obligatorio) o o (cero/opcional).
               * Lado de "Muchos": { (muchos).
               * Línea: -- (relación fuerte/identificativa) o .. (relación débil).
Ejemplo práctico en código Mermaid:


erDiagram
    CLIENTE ||--o{ PEDIDO : "realiza"
    PEDIDO ||--|{ DETALLE_PEDIDO : "contiene"
    PRODUCTO ||--o{ DETALLE_PEDIDO : "aparece en"
	



¿Cómo se lee este código?
               1. CLIENTE a PEDIDO: Un Cliente puede tener cero o muchos pedidos (o{), pero un Pedido debe pertenecer a uno y solo un cliente (||).
               2. PEDIDO a DETALLE: Un Pedido debe tener al menos uno o muchos detalles (|{).

Modelado Dimensional: qué es y para qué existe
Concepto previo: Agregaciones
Las agregaciones consisten en compilar y resumir datos detallados para obtener información a un nivel de análisis más alto.
Una analogía útil es pensar en el reporte semanal de un restaurante.
Un restaurante registra miles de transacciones cada día. Cada pedido contiene información detallada como:
               * qué plato se pidió

               * cuánto costó

               * a qué hora se pidió

               * qué mesero atendió

               * qué mesa lo solicitó

Estos registros representan datos transaccionales detallados.
Debido al gran volumen de datos, analizar cada registro individualmente no permite ver tendencias fácilmente.
Por eso se utilizan agregaciones.

COUNT(*)
FROM FACT_INSCRIPCIONES f
JOIN DIM_CARRERA ca
ON f.carrera_sk = ca.carrera_sk
GROUP BY ca.nombre_carrera;

¿Qué es el modelado dimensional?
El modelado dimensional es una forma de estructurar datos pensada para análisis (OLAP/BI): reportes, tableros, KPIs, exploración, agregaciones, tendencias.
Su idea central es simple:
                                       * Guardar eventos medibles (ventas, pagos, matrículas, llamadas, envíos) en una tabla central.

                                       * Rodearlos de contexto descriptivo (quién, qué, cuándo, dónde, cómo, bajo qué condiciones) en tablas alrededor.
Esto optimiza:
                                          * Facilidad de consulta (SQL más simple)

                                          * Rendimiento en agregaciones. 

                                          * Entendimiento por negocio (modelo intuitivo)

En OLTP normalizamos para evitar redundancia; en OLAP aceptamos cierta redundancia para consultar más rápido y más fácil.
________________


Concepto base: “¿Qué queremos medir?” vs “¿Cómo lo describimos?”
El pensamiento dimensional arranca con dos preguntas:
                                             1. ¿Qué evento o proceso del negocio quiero analizar?
 → eso define los hechos

                                             2. ¿Desde qué perspectivas lo quiero analizar?
 → eso define las dimensiones

________________


1) Tabla de Hechos (Fact)
1.1 Qué es un hecho
Un hecho es un evento del negocio que ocurre y que normalmente deja:
                                                * una o más métricas (medidas)

                                                * referencias a dimensiones que describen el contexto

Ejemplos de hechos:
                                                   * Una venta

                                                   * Un pago

                                                   * Una transacción bancaria

                                                   * Una matrícula (como evento)

                                                   * Un embarque/envío

                                                   * Una atención en mesa de ayuda

                                                   * Una lectura de sensor

La tabla de hechos responde a:
“Qué pasó” y “cuánto”.
________________


1.2 Qué contiene una tabla de hechos
Una tabla de hechos casi siempre contiene:
A) Claves hacia dimensiones (Foreign Keys)
Son los “punteros” al contexto:
                                                      * id_cliente

                                                      * id_producto

                                                      * id_tienda

                                                      * id_tiempo

                                                      * etc.

En BI es muy común usar claves sustitutas (surrogate keys), no la clave natural del sistema fuente. (Ej.: cliente_sk en vez de id_cliente_erp).
B) Medidas (Measures)
Son los valores numéricos que queremos agregar:
                                                         * cantidad

                                                         * importe_total

                                                         * costo

                                                         * descuento

                                                         * impuestos

                                                         * duracion_segundos

                                                         * etc.

C) (A veces) atributos degenerados
Un identificador que pertenece al evento pero no amerita dimensión:
                                                            * número de factura

                                                            * número de pedido
Se guarda directamente en el hecho: numero_factura.

________________


1.3 Grano (Grain): el concepto más importante del modelado dimensional
El grano (granularity) es la definición exacta de qué representa una fila en la tabla de hechos.
Esto debe quedar clarísimo porque determina todo:
                                                               * qué medidas son válidas

                                                               * qué dimensiones debes incluir

                                                               * qué consultas serán posibles

Ejemplos de granos:
                                                                  * “Una fila por línea de factura”
(Factura #123, Producto X, 2 unidades…)

                                                                  * “Una fila por venta por ticket”
(un ticket como total, sin detalle por producto)

                                                                  * “Una fila por transacción bancaria”

                                                                  * “Una fila por lectura de sensor cada minuto”

👉 Regla didáctica:
Si no puedes decir en una frase qué representa una fila, el modelo no está listo.
________________


1.4 Tipos de tablas de hechos 
a) Hechos transaccionales
Un registro por evento (los más comunes).
                                                                     * Venta

                                                                     * Pago

                                                                     * Envío

✅ Buenas para “qué pasó” y “cuánto”.
b) Hechos de snapshot periódico
Un registro por período regular (diario, mensual).
Ej.: “saldo diario por cuenta”.
✅ Buenas para series de tiempo y estado por día.
c) Hechos de snapshot acumulativo
Registra el avance de un proceso con hitos.
Ej.: “orden: creada → enviada → entregada”.
✅ Buenas para medir tiempos de ciclo y etapas.
________________


2) Dimensiones (Dimension)
2.1 Qué es una dimensión
Una dimensión es una entidad descriptiva que da contexto a los hechos.
Responde a:
                                                                        * Quién

                                                                        * Qué

                                                                        * Cuándo

                                                                        * Dónde

                                                                        * Cómo

                                                                        * Por qué (a veces como atributo categórico)

Ejemplos de dimensiones:
                                                                           * Cliente (segmento, edad, ciudad)

                                                                           * Producto (categoría, marca)

                                                                           * Tiempo (día, mes, trimestre, año)

                                                                           * Tienda / Sucursal

                                                                           * Vendedor

                                                                           * Canal (web, tienda física)

                                                                           * Geografía

Las dimensiones están llenas de atributos textuales/categóricos que sirven para:
                                                                              * filtrar

                                                                              * agrupar

                                                                              * segmentar

                                                                              * hacer drill-down / roll-up

________________


2.2 Dimensión = “tabla ancha” (wide)
A diferencia del OLTP normalizado, en dimensional una dimensión suele ser “ancha”:
DimProducto:
                                                                                 * producto_sk

                                                                                 * sku

                                                                                 * nombre

                                                                                 * marca

                                                                                 * categoría

                                                                                 * subcategoría

                                                                                 * tamaño

                                                                                 * color

                                                                                 * proveedor

                                                                                 * etc.

Esta desnormalización es intencional: evita joins innecesarios y hace el modelo más amigable.
________________


2.3 Dimensión Tiempo: casi siempre existe
En BI la dimensión tiempo suele ser una tabla preconstruida con atributos como:
                                                                                    * fecha

                                                                                    * día de semana

                                                                                    * nombre del mes

                                                                                    * semana del año

                                                                                    * trimestre

                                                                                    * feriado (sí/no)

                                                                                    * etc.

Esto facilita reportes sin recalcular calendarios.
________________


2.4 Jerarquías en dimensiones
Las dimensiones suelen tener jerarquías naturales para análisis:
                                                                                       * Producto: categoría → subcategoría → producto

                                                                                       * Geografía: país → provincia → ciudad

                                                                                       * Tiempo: año → trimestre → mes → día

Esto soporta análisis tipo:
                                                                                          * “ventas por mes”

                                                                                          * “ventas por trimestre”

                                                                                          * “ventas por año”

________________


3) Diferencia exacta: Hecho vs Dimensión (sin ambigüedad)
Regla práctica infalible
                                                                                             * Si el dato es algo que mides y agregas (suma, promedio, conteo), es hecho.

                                                                                             * Si el dato es algo que describe y te sirve para filtrar/segmentar, es dimensión.

Ejemplos claros:
                                                                                                * “Monto” → hecho

                                                                                                * “Cantidad” → hecho

                                                                                                * “Nombre del cliente” → dimensión

                                                                                                * “Ciudad” → dimensión

                                                                                                * “Fecha” → dimensión (o clave a dimensión tiempo)

                                                                                                * “Estado del pedido” → normalmente dimensión (o atributo en dimensión pedido)

4. Esquemas: Star vs. Snowflake
Característica
	Star Schema (Estrella)
	Snowflake Schema (Copo de Nieve)
	Estructura
	Una Fact rodeada de Dimensiones simples.
	Dimensiones normalizadas (se dividen en más tablas).
	Performance
	Muy rápida (pocos Joins).
	Más lenta (muchos Joins).
	Mantenimiento
	Más difícil (datos duplicados).
	Más fácil (datos organizados).
	Uso Ideal
	Data Warehouses modernos (Snowflake, BigQuery).
	Sistemas con espacio de almacenamiento limitado.

  5. Slowly Changing Dimensions (SCD)
En el análisis, la realidad cambia. Un cliente puede mudarse de ciudad. ¿Cómo manejamos ese cambio en el histórico?
                                                                                                   * SCD Type 0 (Fixed): El dato nunca cambia (ej. Fecha de nacimiento).
                                                                                                   * SCD Type 1 (Overwrite): Se sobrescribe el dato viejo. Perdemos el historial.
                                                                                                   * SCD Type 2 (Add New Row): Se crea una nueva fila con una fecha de inicio y fin. Es el estándar de la industria para mantener historial.

Preguntas Frecuentes (FAQ) sobre Modelado Dimensional
1. ¿Por qué no simplemente crear una Vista (View) en la base de datos transaccional (OLTP)?
Si bien una vista puede realizar agregaciones y joins (uniones) sobre las tablas transaccionales, esta aproximación tiene serias limitaciones para el análisis a gran escala:


Característica
	Vista sobre OLTP (Transaccional)
	Modelado Dimensional (OLAP/Data Warehouse)
	Rendimiento
	Lento. La vista recalcula los joins y agregaciones cada vez, afectando las transacciones en vivo (escritura).
	Rápido. Los datos ya están pre-calculados, desnormalizados y optimizados para lectura.
	Impacto OLTP
	Alto. El sistema transaccional (que debe ser rápido para ventas, registros, etc.) se ralentiza al atender consultas analíticas pesadas.
	Nulo. El análisis ocurre en un sistema separado (Data Warehouse).
	Historial
	Difícil de manejar. Los cambios en las dimensiones (ej. un cliente se muda) afectan el historial si no se implementa una lógica SCD compleja en la vista.
	Nativo. El uso de SCD Type 2 en las dimensiones asegura que el historial se preserve fácilmente.
	Complejidad
	El SQL de las vistas analíticas se vuelve extremadamente complejo.
	El SQL de consulta es simple (pocos joins directos de hecho a dimensión).
	

Conclusión: Las vistas OLTP son adecuadas para reportes simples en tiempo real, pero fallan catastróficamente para el análisis de grandes volúmenes de datos históricos o complejos.
2. ¿Por qué no solo hacer una consulta grande (query) y jalar los datos directamente al sistema transaccional?
El objetivo principal de un Data Warehouse y el Modelado Dimensional es separar la carga de trabajo.


Razón Principal
	Explicación
	Separación de Cargas
	Las bases de datos transaccionales (OLTP) están optimizadas para escritura rápida (insertar una venta, actualizar un registro). Las consultas analíticas (OLAP) son cargas de trabajo de lectura pesada. Ejecutar una consulta grande directamente en el OLTP consume recursos que deberían estar dedicados a las operaciones diarias del negocio, lo que resulta en lentitud y caídas del sistema.
	Consolidación
	El sistema transaccional suele estar fragmentado (varias bases de datos, sistemas legados). El Data Warehouse (con su modelo dimensional) sirve como el punto único de la verdad, donde todos los datos se limpian, transforman y consolidan de antemano para el análisis.
	Optimización Analítica
	El modelo dimensional (Star Schema) es intrínsecamente más rápido para la agregación que la estructura normalizada (ER Model) del sistema transaccional. La desnormalización reduce drásticamente la cantidad de joins necesarios.
	

En resumen: Jalar datos directamente de un OLTP para un análisis masivo es ineficiente y peligroso para la estabilidad del sistema operacional. El Modelado Dimensional provee una estructura robusta y dedicada para este fin.


🧠 Tips Nemotécnicos y Ayudas de Memoria
                                                                                                                  * Hechos vs Dimensiones (Las preguntas):
                                                                                                                  * Los Hechos (Facts) responden a: "¿Cuánto?" (Ventas, Cantidad, Precio).
                                                                                                                  * Las Dimensiones responden a: "¿Quién?, ¿Cuándo?, ¿Dónde?, ¿Qué?".
                                                                                                                  * La Regla de la Estrella:
                                                                                                                  * Si para sacar un reporte necesitas hacer más de 2 Joins para llegar a una descripción, no es una estrella pura, se está convirtiendo en un copo de nieve.
                                                                                                                  * SCD Type 2: Recuerda el número 2 como "2 filas para la misma persona" (la vieja y la nueva).
